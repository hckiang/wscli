#+TITLE: wscli – RFC 6455 WebSocket Client for Common Lisp
#+OPTIONS: toc:t

A multi‑threaded, thread‑safe WebSocket client library that strictly follows RFC 6455.  
It features a background listener thread, automatic ping/pong handling, UTF‑8 validation, and a correct closing handshake with timeout.

* Features

- Full RFC 6455 compliance (control frames, fragmentation, masking, close codes).
- Secure connections (WSS) via ~cl+ssl~ with SNI support.
- Thread‑safe design: one dedicated listener thread, arbitrary user threads can send frames or close the connection safely.
- Automatic background message loop; alternatively, run the loop manually in the calling thread.
- Callback‑based handler: receive events for text, binary, ping, pong, and close.
- Optional subprotocol negotiation.
- Closing handshake with configurable timeout and safe forced‑close fallback.

* Dependencies

- [[https://common-lisp.net/project/usocket/][usocket]] – TCP sockets.
- [[https://github.com/cl-plus-ssl/cl-plus-ssl][cl+ssl]] – SSL/TLS for secure connections.
- [[https://github.com/sharplispers/ironclad][ironclad]] – cryptographic randomness and SHA‑1.
- [[https://github.com/cl-base64/cl-base64][cl-base64]] – Base64 encoding.
- [[https://github.com/cl-babel/babel][babel]] – UTF‑8 encoding/decoding.
- [[https://github.com/sionescu/bordeaux-threads][bordeaux‑threads]] (~bt~) – locks and condition variables.
- [[https://github.com/quri/quri][quri]] – URL parsing (only for ~connect-url~).

* API

** Connection object

A ~websocket-connection~ instance is created by ~connect~ or ~connect-url~.  
Accessors:
- ~conn-state~ → ~:open~, ~:closing~, or ~:closed~
- ~conn-subprotocol~ → the negotiated subprotocol (string or ~nil~)
- ~conn-closed-p~ → predicate, returns ~t~ when the connection is not open.

** ~connect~ host port path &key handler background origin protocols secure verify hostname

Establish a WebSocket connection. Returns the connection object.

- ~host~, ~port~ – server address.
- ~path~ – resource path, e.g. ~"/chat"~.
- ~handler~ – a function of two arguments (type, data) called for incoming messages.
- ~background~ – if true (default) starts the listener in a separate thread.
- ~origin~ – optional ~Origin~ header.
- ~protocols~ – list of subprotocol strings to offer.
- ~secure~ – ~t~ for WSS (TLS).
- ~verify~ – passed to ~cl+ssl:make-ssl-client-stream~ (default ~nil~).
- ~hostname~ – optional SNI hostname (defaults to ~host~).

** ~connect-url~ url &rest args

Parses ~ws://...~ or ~wss://...~ URLs and calls ~connect~.  
All other keyword arguments are passed through.

#+begin_src lisp
(connect-url "wss://echo.websocket.org")
#+end_src

** Handler callback

The handler function receives two values:
- Event type – a keyword: ~:text~, ~:binary~, ~:ping~, ~:pong~, or ~:close~.
- Payload – a string for ~:text~, a ~(simple-array (unsigned-byte 8))~ for ~:binary~/~:ping~/~:pong~, and the close code for ~:close~.

#+begin_src lisp
(defun my-handler (type data)
  (format t "~&[WS] ~A → ~S~%" type data))
#+end_src

** ~close-connection~ conn &optional code reason

Initiate the WebSocket closing handshake (non‑blocking).  
Default close code is 1000 (normal closure).  
~reason~ is a UTF‑8 string, truncated to ≤ 123 bytes.  
After calling this, the connection state becomes ~:closing~ and will eventually transition to ~:closed~ (either after the peer replies or after the timeout).

** ~wait-until-closed~ conn &optional timeout

Block the calling thread until the connection reaches ~:closed~.  
~timeout~ in seconds, ~nil~ means wait forever. Returns ~t~ on success, ~nil~ on timeout.

** ~send-text~ conn string

Send a text frame. String is encoded as UTF‑8.

** ~send-binary~ conn octets

Send a binary frame. Octets must be a ~(unsigned-byte 8)~ array.

** ~send-ping~ conn &optional payload

Send a ping control frame. Payload ≤ 125 bytes.  
The listener automatically replies with a pong; the user handler receives a ~:pong~ event.

** ~run-message-loop~ conn

If the connection was created with ~:background nil~, call this function in your thread to start the reading loop (blocks until the connection closes).

* Examples

** Secure echo test

#+begin_src lisp
(defun handler (type data)
  (print (list type data)))

(defparameter *conn* (connect "echo.websocket.org" 443 "/"
                              :secure t
                              :handler #'handler))

(send-text *conn* "Hello, WebSocket!")

;; After the echo comes back, close it.
(close-connection *conn*)
(wait-until-closed *conn*)
#+end_src

** Binance trade stream (background listener)

#+begin_src lisp
(defparameter *binance*
  (connect-url "wss://stream.binance.com:9443/stream?streams=btcusdt@trade"
               :secure t
               :handler #'handler))

;; The listener runs in the background, printing trades.
;; Later, shut it down:
(close-connection *binance*)
#+end_src

** Foreground loop (no background thread)

#+begin_src lisp
(defparameter *conn* (connect "localhost" 8080 "/ws"
                              :background nil
                              :handler #'handler))
;; This blocks until the connection closes:
(run-message-loop *conn*)
#+end_src

** Handling different event types

#+begin_src lisp
(defun my-handler (type data)
  (case type
    (:text   (format t "Text: ~a~%" data))
    (:binary (format t "Binary: ~a bytes~%" (length data)))
    (:ping   (format t "Ping: ~a~%" data))
    (:pong   (format t "Pong: ~a~%" data))
    (:close  (format t "Closed with code ~d~%" data))))
#+end_src

* Thread‑safety

- The library uses a single lock (~conn-lock~) to protect internal state.
- The listener thread never invokes user code while holding the lock; you can safely call ~close-connection~, ~send-text~, etc. from inside the handler without deadlocking.
- All writes from application threads are serialised and checked against the connection state; an error is signalled if the connection is not open (control frames are still allowed during the closing handshake).
- The closing timeout thread ensures the listener never blocks forever waiting for the peer’s close response.
- Multiple concurrent calls to ~close-connection~ are harmless; only the first one takes effect.

* Closing behaviour

RFC 6455 mandates an orderly closing handshake:
1. Application calls ~close-connection~ → a close frame is sent, state → ~:closing~.
2. The peer replies with its own close frame; the listener state → ~:closed~ and the socket is closed.
3. If the peer never replies, a separate watchdog thread closes the socket after ~close-timeout~ seconds (default 1.5 s), transitioning the connection to ~:closed~.

Calling ~close-connection~ from inside the handler (e.g. in response to a server message) is perfectly safe.
